## 二、致命项：照方案删 `aimin-cache` 会把 admin 打挂

原报告 C7 写的是"零消费者，最干净的删除项，-1166 行"。**这条是错的。**

我当时的取证方法是按类名 grep（`AiminCache|AiminCacheManager`），四个模块 0 命中。但我漏了一类依赖：**注解间接依赖的 Bean**。

重新取证：

| 证据 | 位置 |
|---|---|
| admin 开启了缓存 | `AiminAdminApplication.java:11` → `@EnableCaching` |
| 9 处 `@Cacheable(keyGenerator = "keyGen")` | `AdminRoleServiceImpl.java:38,51,57,63,69,75`、`AdminServiceImpl.java:83,104,110` |
| 还有 `@CacheEvict(allEntries = true)` | `AdminRoleServiceImpl.java:81` |
| `keyGen`、`defaultKeyGen` 这两个 KeyGenerator Bean **由 aimin-cache 提供** | `AiminCacheAutoConfiguration.java:93` → `@Bean(name = {"keyGen", "defaultKeyGen"})` |
| `CacheManager` 也由它提供 | `AiminCacheAutoConfiguration.java:69` → `AiminCacheManager` |
| 且该模块通过自动装配声明生效 | `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` |

**后果**：删掉模块 → admin 容器启动时找不到名为 `keyGen` 的 `KeyGenerator` → `NoSuchBeanDefinitionException`（或退化成默认 `ConcurrentMapCacheManager`，L2 Redis 与缓存同步静默失效）。无论哪种，都不是"删掉 1166 行死代码"，而是"删掉 admin 的缓存层"。

**为什么会判错**：我把"低耦合"理解成了"类名 grep 不到就没关系"。真正的低耦合检查要看**注解、SPI、自动装配、配置键**这四类隐形引用。这恰好是我在报告里批评别人的那个毛病——只看见显式的 import，看不见运行时的装配。

**修正**：`aimin-cache` 保留。要减法就去看 `aimin-auth`（见 B1）。

## 三、方向反了：双 RRF 不是"计分两次"，是"名额被药品兑换"

原报告 C1 说"知识库条目被计分两次、权重被抬高、药品证据可能被整批挤掉"。**这三句都不成立，而且方向反了。**

关键证据在 `RrfFusion.java:31`：

```java
double s = 1.0 / (K + rank + 1);   // 只读 rank，从不读 ev.score()
```

RRF 是**纯名次函数**，它根本不看传进来的分数。所以：

- ❌ "知识库被计两次分" —— 不存在，分数不累加；
- ❌ "权重被抬高" —— 不存在，第二层融合把第一层的分数整个丢弃了；
- ❌ "药品被整批挤掉" —— 反了，药品恰恰是被抬上来的那一方。

**真实后果（逐位算一遍）**：知识库 ≤5 条占名次 0–4（1/61…1/65），药品 ≤3 条占名次 0–2（1/61…1/63）。降序排列（同分按插入顺序，知识库先入）：

| 名次 | 条目 | 分值 |
|---|---|---|
| 1 | 知识库 k0 | 1/61 |
| 2 | 药品 d0 | 1/61 |
| 3 | 知识库 k1 | 1/62 |
| 4 | 药品 d1 | 1/62 |
| 5 | 知识库 k2 | 1/63 |
| — | 药品 d2 | 1/63（被插入顺序挤掉） |

`topK=5` 的结果是 **3 条知识库 + 2 条药品**——知识库从 5 条被压到 3 条。前两条药品各自兑换掉一个知识库名额（第 3 条与 k2 同分 1/63，靠插入顺序被挤掉），**而且整个兑换过程与药品自身分数无关**：一条 0.1 分的弱命中，和一条 20 分的强命中，拿到的名次分一模一样。

**真正的病根在这两行**：

- `DrugRetriever.java:81` —— `if (score > 0)` 即入选，**药品侧零阈值**；
- `RrfFusion` 只看名次，于是 `HybridRetriever` 里辛苦标定的 `min-vector-score=0.88` / `min-bm25-score=6.5` 在第二层**被整体作废**。

所以最终进入提示词的准入条件，从"证据够不够好"退化成了"药品库有没有任意一条弱命中"。这比原报告的判断严重，但**修法完全不同**：光"把融合合并成一次"没用，必须同时给药品补门控 + 名额上限，否则合并后药品照样按名次抢位。

**风险提示**：给药品加阈值后，评测里的 `药品 12/12` 很可能掉到 11/12。这是"指标变差但系统变对"，必须接受并记录，不能为了保 12/12 拒绝修。

> **实测后修正（见 [`双RRF影响实测.md`](双RRF影响实测.md)）**：本节暗示"名额挤压来自第二层融合"，这一点**不准确**。模拟「只做一层 RRF，KB 15 条 + 药品 3 条」的结果仍是 **3 KB + 2 药品**——挤压的真正来源是 **RRF 对异构召回源做名次平权**（药品只要有命中就按名次抢走约一半名额），不是融合次数。因此"合并成一次"只能修好门控失效与双份维护，**修不好名额挤压**；后者要靠"KB 优先补位"或"药品名额上限"。
> 另：q58「汽车保养」实测漏拒答（药品凭"一次"命中 3 条），且**只删第二层融合也照样漏**——拒答判定必须改成只看 KB。

## 四、自相矛盾：那条验收标准锁死了自己

原文验收标准第 2 条：

> 60 题评测 Recall@5 ≥ 0.967 …… 且评测与线上走同一个 `RetrievalFacade`

这两半互斥。

- 现在的 `recallAt5 = 0.967 (29/30)`，测的是 `EvaluationRunner` 里 `hybridRetriever.retrieve()` —— **知识库独占 5 个名额**的成绩。
- 一旦让评测也走 `RetrievalFacade`（合并结果），知识库只剩 3 个名额（见第三节），`29/30` 必然掉。

也就是说：**按方案改完，那条 ≥0.967 的线一定过不了**；如果它过了，说明 `RetrievalFacade` 根本没真正接上。

**修正（口径分层）**：

```
RetrievalFacade
├── retrieveKnowledge(query, k)   ← fact / MRR 用它（KB 召回能力，口径不变，可对比 0.967）
├── retrieveMerged(query, k)      ← 线上对话用它（含药品、含门控、含名额上限）
└── refusalGate(merged)           ← 拒答判定用它
```

"统一入口"不等于"所有指标都走同一个方法"——**指标口径必须跟它要度量的能力对齐**。原报告把这两件事混成一句"都只依赖它"，是我自己犯的"过度归一"。

## 五、成本判断反了：`aimin-base` 不是一行 pom，是引狼入室

原报告 C3 的结论是"一行依赖声明 + 9 处替换，投入产出比最高"。**成本被严重低估。**

`aimin-common/aimin-base/pom.xml` 实际带入：

```
spring-cloud-starter-alibaba-nacos-discovery
spring-cloud-starter-alibaba-nacos-config
spring-cloud-starter-bootstrap
spring-boot-starter-data-elasticsearch
mybatis-plus-join-boot-starter
mybatis-plus-spring-boot3-starter
```

而 agent 现在**刻意**做了一件事来保持轻量：`AgentApplication` → `@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)`。

**先自我纠错**：我一开始想写"agent 启动命令里没有 `SPRING_CLOUD_NACOS_*_ENABLED=false`，所以加 base 会去连 Nacos"——**这句不准确**。README:67 是四个进程**共用**的 `export`，agent 也拿到了。按 README 的路径启动，Nacos 是被压住的。

真正的问题因此变成三条，都比"启动即挂"轻，但都不该接受：

1. **这份 suppression 只活在 README 的 shell 习惯里，不在模块自身**。从 IDE run configuration、Dockerfile、`nohup java -jar` 任一方式启动，agent 就会去注册 Nacos、拉配置——一个当前完全不依赖注册中心的服务，变成"必须先懂这套开关才能启动"。
2. **`spring-boot-starter-data-elasticsearch` 不受那两个开关约束**，硬进 classpath。Spring Boot 3 的 ES 客户端建 bean 时通常懒连接、不一定当场失败，但 agent 从此多一个指向 `localhost:9200` 的配置面，启动排障成本上升。
3. **`mybatis-plus-spring-boot3-starter` 与 `exclude = DataSourceAutoConfiguration` 是语义冲突的**：一边排除数据源，一边引入要求数据源的 ORM 自动装配。当下靠 `@ConditionalOnSingleCandidate(DataSource.class)` 不激活，但这是"靠条件注解碰巧不炸"，不是设计。

**修正（三选一，按成本升序）**：

| 方案 | 成本 | 代价 |
|---|---|---|
| agent 内置 `record ApiResponse<T>(int code, String msg, T data)` | 10 行 | 与 base 的 `Result` 形状双写，但 agent 本来就不共享任何公共类 |
| 抽 `aimin-contract`（零依赖，只放 Result/ApiResponse + 错误码） | 1 小时 | 多一个模块 |
| 依赖 base | 1 行 pom | 上述三条 |

**推荐第一项**。判据很简单：agent 与其他模块**共享的不是代码，是 JSON 形状**；共享形状用 10 行 record 就够，没必要共享 classpath。

## 六、诊断过度：921 行里 570 行是 SCSS

原报告把 `views/agent/index.vue` 判为"上帝组件"。按行数拆分看：

| 文件 | 模板 | 脚本 | **样式** | 合计 |
|---|---|---|---|---|
| `views/agent/index.vue` | 120 | 228 | **570** | 921 |
| `views/dashboard/index.vue` | 142 | 185 | **485** | 816 |

真正的逻辑是 228 行 / 185 行——**在正常范围内**。按原方案"单 `.vue` ≤ 400 行"的验收标准，唯一能满足的做法是把 SCSS 搬进独立文件：行数达标、内聚不变、评审时还得跳文件看样式。这是典型的**指标替代目标**。

## 七、漏项

### B1 · `aimin-auth` 是比 cache 大得多的减法，方案里一个字没提

| 事实 | 证据 |
|---|---|
| 前端全库 0 次调用 | `grep -rn "aimin-auth" admin-front/src admin-front/vite.config.js` → 无命中 |
| 网关仍挂着路由与端口 | `bootstrap.yml:20-23` → `uri: http://127.0.0.1:8081` |
| 启动必须喂假参数 | README：`WX_APPID=wx0000000000000000 WX_SECRET=dummy` |
| 项目自认未接入 | README「aimin-auth ─ 微信登录 :8081（网页端暂未接入）」 |

18 个 Java 文件 + 一个常驻进程 + 一条网关路由 + 一组必填假配置，服务的是一个"暂未接入"的功能。它比 `aimin-cache` 更该被讨论——而我的报告因为把范围锁在 "agent + admin"，整块跳过了。

**但这不只是技术判断**：微信登录是否在路线图上，只有你能定。见 Q3。

### B2 · `refId` 的格式副作用没写进改动清单

- `RrfFusion.java:46` 把编号统一成 `"[" + i + "]"`；
- `HybridRetriever` 产出的是 `"v" + rank`；
- 前端 `views/agent/index.vue:67-68` **直接渲染** `ev.refId` 作为角标。

方案说"融合只在 `RrfFusion` 做一次"，但没说编号在哪儿补。若不补，证据卡角标会变成 `v1`、`v2`,与正文里 `[1]` 的引用对不上。

### B3 · 指标与文档同步不在计划里

改完检索后，需要同步的位置清单（原方案一个都没列）：

- `README.md` 的「离线评测集 60 题 …… Recall@5 0.967」
- `docs/架构说明.md` 4.4 的 RRF 流程图（现已与代码不符）
- `admin-front` 首页指标卡（读的是接口，无硬编码，安全）
- `server/data/eval/latest.json` 与 `regression.md` 的口径说明

项目对外的可信度就架在这些数字上。改了算法不同步文档，等于给自己留了笔假账。

## 八、对我自己方案的过度设计指控

原方案把 `MedicalAgentService` 拆成 6 个类。按"是否值得一个类"重新审：

| 拟拆出 | 体量 | 判据 | 结论 |
|---|---|---|---|
| `RiskGate` | ~40 行 + 状态 | 有独立状态与生命周期，未来换 Redis | **拆** |
| `PromptAssembler` | ~40 行 | 纯函数、prompt 会频繁调、现在完全不可测 | **拆** |

| `IntentClassifier` | 10 行正则 | 一个正则不值得一个类 | 留私有方法 |

## 九、执行顺序也错了：先动刀再测量，delta 无法归因

原方案：改管线（批 1）→ 抽 facade → 重跑评测"确认不回归"。

问题：第 1 步同时改了两件事（融合次数 + 药品是否设阈值），第 3 步又换了评测口径。三个变量一起动，`0.967 → X` 这个差值**归因不了**——是算法退步、还是口径变化、还是两者相抵，说不清。而"确认不回归"恰恰要求能归因。

**环境已核实可跑**（这是原报告没做、我这次补的）：`aimin-agent.jar` 构建于 2026-10-25 18:02、MySQL 3306 与 Redis 6379 均在监听、`data/eval/questions.json` 与 `agent-embeddings.json` 齐备。

**改为四个可归因的步骤，每步一个提交、一个数字**：

| 步 | 动作 | 期望 |
|---|---|---|
| 0 | 用现有 jar 跑基线 | 复现 0.967 / 1.0 / 1.0 / 1.0，存档 `baseline.json` |
| 1 | 只抽 `RetrievalFacade`（纯搬迁、行为不变） | 数字与步 0 **完全一致**（验证搬迁无副作用） |
| 2 | 只改药品门控 + 名额上限 | 药品可能 12/12 → 11/12，记录；KB 名额不再被侵蚀 |
| 3 | 只改评测口径（fact 走 `retrieveKnowledge`） | 分离"口径差异"与"算法差异"，得出新基线 |
