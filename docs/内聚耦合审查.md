# aimin 高内聚 / 低耦合审查

> 审查范围：`server/`（4 个业务模块 + 5 个 common 模块，约 140 个 Java 文件 / 9.2k 行）、`admin-front/src`（27 个文件 / 6.5k 行）。
> 审查口径：**只评结构质量**——一处改动要碰几个类、一个类有几个变化的理由、两个模块之间知道彼此多少。
> 与 [`优化方案.md`](优化方案.md) 的分工：那份管安全与功能缺陷（P0 鉴权、令牌绑定、路径穿越等），本份不重复；本份管"改起来疼不疼"。

> ⚠️ **勘误（2026-10-26，见 [`方案对抗性审查.md`](方案对抗性审查.md)）**
> 本文有 4 处结论经对抗性复核后被推翻或修正，**请连同勘误一起阅读**：
> 1. **C7 撤回**：`aimin-cache` 不是死模块——admin 有 9 处 `@Cacheable(keyGenerator="keyGen")`，`keyGen` 与 `CacheManager` 均由它的自动装配提供，删除会打挂 admin。原判断错在只按类名 grep，漏了注解间接依赖的 Bean。
> 2. **C1 改写**：`RrfFusion` 只读 rank、从不读 `score()`，"被计两次分/权重被抬高"不成立；真实后果是**药品凭名次兑换知识库名额**（5 条压到 3 条），且药品侧零阈值。修法必须含"药品门控"，仅合并融合无效。
> 3. **C3 成本修正**：`aimin-base` 会拖进 Nacos discovery/config + ES starter + mybatis-plus；而 agent 刻意 `exclude` 了 `DataSourceAutoConfiguration`。"一行 pom"不成立，改在 agent 内置 `ApiResponse`。（附注：README 里 `SPRING_CLOUD_NACOS_*_ENABLED=false` 是四服务共用的 export，所以 Nacos 是被压住的；风险在于这份压制只活在 README 的 shell 里、且管不到 ES starter。）
> 4. **H5 降级**：921 行里 570 行是 SCSS，脚本仅 228 行，不构成"上帝组件"；"单 .vue ≤400 行"这条验收作废。
> 验收标准中的 "Recall@5 ≥ 0.967" 同样作废——新口径下 KB 名额变少，该门槛不可能达成，详见对抗性审查第四节。
> 5. **批次表已被取代**：第六节的四批执行计划由 [`优化方案-v2.md`](优化方案-v2.md) 统一编排（顺序、依赖、验收均已重排）。本文只保留"诊断"，不再作为执行依据。

## 一、结论

| 维度 | 评价 | 说明 |
|---|---|---|
| 模块级边界 | **好** | 网关 / 管理 / 认证 / Agent 四服务职责清楚，Agent 依赖最少，可独立部署 |
| 包级边界 | **良** | agent 侧 `retrieval / risk / llm / memory / eval` 分得干净；admin 侧 controller/facade/service/mapper 基本成立 |
| 类级内聚 | **差** | 4 个类承担 5 个以上变化理由：`MedicalAgentService`、`IngestionService`、`AgentPersistenceService`、`PermissionFacadeService` |
| 算法唯一性 | **差** | RRF 有两份实现、两套去重 key、两个 K 常量，且线上跑的是"融合两次" |
| 契约一致性 | **差** | 响应信封手写 9 处，项目里的 `Result<T>` 用不上（agent 压根不依赖 common） |
| 可测性 | **中** | 纯函数层（RRF / BM25 / 风险 / 脱敏 / 记忆）有单测；编排层 0 覆盖，且测试被迫 `extends` 具体类 |
| 前端内聚 | **差** | 4 个 view 均 450–920 行，SSE 事件路由、SVG 图表数学、会话标题回写都写在页面里 |

**一句话**：模块切得对，类切得不对。跨服务边界是低耦合的，服务内部是"一个类干完全程"的高耦合。

## 二、内聚问题（一个类有太多变化的理由）

### H1 · `MedicalAgentService` — 编排器兼了 6 件事（最严重）

`server/aimin-agent/.../service/MedicalAgentService.java`（382 行，7 个构造依赖）

| 职责 | 位置 | 独立的变化理由 |
|---|---|---|
| SSE 通道管理（send/finish/断连抑制） | 90–107 | 换协议、加心跳 |
| 入参校验（空值、2000 字上限） | 110–119 | 产品改限制 |
| 意图识别（问候正则） | 143–153 | 加闲聊/寒暄分类 |
| 风险门控 + 待确认令牌存储（TTL / 上限 / 原子消费） | 156–170, 288–316 | 令牌换 Redis、改 TTL |
| 检索编排 + 拒答判定 | 175–200 | 换召回策略 |
| 提示词拼装（证据格式化 / 历史 / 编号约束） | 202–221, 49–56 | 调 prompt、换模板 |
| 记忆读写 + 落库 | 363–371 | 换存储 |

后果不是"不好看"，是**改一处要读全篇**：调 prompt 得翻过 200 行 SSE 和风控代码；而这段编排没有一行单测——因为它 new 不出来（要 7 个真实依赖 + `SseEmitter`）。

**建议拆分**（按变化方向切，不按代码行数切）：

```
ChatOrchestrator   ← 只剩流程串联，30~50 行，读一遍就懂
├── SseChannel         emitter 包装：send(event) / finish() / isClosed()
├── IntentClassifier   问候/闲聊 → 固定回复
├── RiskGate           PendingAsk 存储 + TTL + 原子消费 + reject
├── PromptAssembler    证据 → 上下文文本 + 历史裁剪 + 编号约束
└── AnswerRecorder     memory.add + persistence.save 的一致性写入
```

`RiskGate` 单独拆出来还有额外收益：它现在是纯内存 `ConcurrentHashMap`，"待确认项重启即失效"这条已知限制，未来换 Redis 只动一个类。

### H2 · `IngestionService` — 从文件校验一路干到向量持久化

`server/aimin-agent/.../service/IngestionService.java`（267 行）

单类覆盖：扩展名白名单 → 文件名净化 → 原文件留档 → PDF 逐页抽取 → 章节切片 → embedding → 写向量库 → 写 BM25 → 写注册表 JSON。

五个变化理由（换解析器、调切片、换 embedding、换向量库、改校验规则）全部汇聚到一个类，且**切片算法 `chunkByHeading` / `flushChunk` 是纯逻辑却拿不到单测**（被 `private` 锁在一个有 IO 依赖的类里）。

**建议**：

```
IngestionService（编排，~60 行）
├── DocumentParser      接口 → PdfParser / TextParser（PDF 逐页逻辑集中）
├── ChunkSplitter       纯函数：text → List<String>（可单测，含 overlap）
└── KnowledgeIndexer    chunk → 写 store + bm25 + registry（一致性由它保证）
```

现状还有个隐性风险：`store.addAll` 成功而 `bm25Index.addAll` 之前抛异常时，向量库和 BM25 已经不一致，而 `persist()` 的失败被两处 `catch (Exception ignored)` 吞掉（250–266）。拆出 `KnowledgeIndexer` 后，这段一致性逻辑才有地方写清楚。

### H3 · `AgentPersistenceService` — 写入、调度、报表、工具函数四合一

`server/aimin-agent/.../service/AgentPersistenceService.java`（174 行）

- 写入路径：`ensureSession` / `saveMessage` / `audit`
- 定时任务：`purgeExpired`（`@Scheduled`）
- **读侧报表**：`countSessions` / `countMessagesByRole` / `countAuditByActions` / `dailyMessageCounts`（118–173）
- 工具函数：`mask`（脱敏）

报表聚合和审计落库是两个关注点：前者会随首页改版频繁变（要不要按天、要不要按药品维度），后者几乎不动（合规要求）。放一起的代价是：为了加一个统计维度，要改一个被风控路径依赖的类。

另外构造器字段叫 `drugJdbcTemplate`，却承载会话/消息/审计三表——命名已经承认了这个 bean 的职责漂移。

**建议**：`AgentRepository`（写）+ `AgentStatsRepository`（读聚合）+ `TextMasker`（脱敏，已有单测正好跟着搬）+ `AuditPurgeJob`（`@Scheduled` 单独成类）。

### H4 · `PermissionFacadeService` — CRUD 校验、树装配、路由装配混在一起

`server/aimin-admin/.../facade/PermissionFacadeService.java`（294 行）

- 权限 CRUD 的业务校验（86–153）
- 两套树装配：`buildTree` / `buildMenuTree` 用 hutool `TreeUtil`，`buildRouterTree` 手写递归（179–294）
- `permKey → name` 的派生逻辑在 `updatePermission`（113–122）和 `createPermission`（143–150）各写一遍，逐字相同
- `TreeNodeConfig` 配置抽了 `buildTreeNodeConfig()`（211），但 `buildPermissionTreeWithRole` 里又内联复制一遍（236–242）

同一类里并存两种树构建手法 + 三处配置重复，说明这里没人整理过。**建议**：抽 `PermissionTreeAssembler`（统一用 hutool 或统一手写，二选一）+ 一个 `deriveName(permKey)` 私有方法。

### H5 · 前端 view 混了页面逻辑与图表引擎（**行数结论已修正**）

| 文件 | 模板 | 脚本 | **样式** | 合计 |

## 三、耦合问题（依赖方向与知识重复）

### C1 · 双份 RRF，线上跑的是"融合两次"（最高优先级）

**证据**

- `retrieval/HybridRetriever.java:39-87`：内部对 vector + bm25 做了一遍 RRF，`RRF_K=60`，去重 key = `snippet` 前 120 字，相对阈值 `0.6` 过滤，**截断到 topK**。
- `retrieval/RrfFusion.java:23-49`：另一份 RRF，`K=60`，去重 key = `type:title:snippet.hashCode()`，截断到 topK。
- `service/MedicalAgentService.java:177-179`：`hybridRetriever.retrieve()` 拿到**已经融合并截断**的结果，再和药品结果丢进 `RrfFusion.fuse()` **第二次融合**。

**实际后果**（逐位算过，非估计）

1. **名额挤压（方向与直觉相反）**：`RrfFusion` 只按名次计分（`1/(K+rank+1)`），**不读传入的 `score`**。知识库 ≤5 条占名次 0–4（1/61…1/65），药品 ≤3 条占名次 0–2（1/61…1/63）。降序排列后 topK=5 的实际构成是 **3 条知识库 + 2 条药品**——知识库被从 5 条压到 3 条，**每条药品命中兑换掉一个知识库名额，且与药品自身分数无关**。
2. **门控被作废**：`HybridRetriever` 里标定的 `0.88 / 6.5` 在第二层失去意义，因为第二层只看名次。而 `DrugRetriever:81` 是 `if (score > 0)` 即入选、**零阈值**。最终准入条件从"证据够不够好"退化成"药品库有没有任意一条弱命中"。
3. **双份真相**：`K=60`、去重语义、阈值三处各自维护，改任一处都不会有编译错误提示。
4. **文档已漂移**：`docs/架构说明.md` 4.4 的流程图仍是"向量 + 药品 → RRF"，与代码（向量+BM25 → RRF → +药品 → RRF）对不上。

**建议**：RRF 只保留 `RrfFusion` 一处。`HybridRetriever` 降级为"召回器"，只返回 `(vectorHits, bm25Hits)` 两路原始列表并各自做阈值门控；融合与 `topK` 截断**只在编排层做一次，且先融合后截断**。
**但仅此不够**：必须同时给药品侧补阈值 + 名额上限，否则合并成一次后药品照样凭名次抢位（详见对抗性审查第三节）。

### C2 · 评测器复制了生产管线，测的不是线上那条路

`eval/EvaluationRunner.java:133-139`：`unanswerable` 题型的拒答判定是 `hybridRetriever.retrieve(...).isEmpty()`。
生产的拒答判定（`MedicalAgentService.java:187`）是 `knowledgeHits + drugHits` 经 RRF 后为空。

两者不等价：一道题可能知识库无命中、但药品有命中 → 线上会答、评测记为"成功拒答"。所以 README 里 `拒答 8/8` 这个数字**跑的是另一条路径**。同理 `fact/drug` 指标也是绕开编排直接调检索器。

**建议**：抽出 `RetrievalFacade`（`retrieve(query, topK) → List<Evidence>`，内含多路召回 + 门控 + 融合 + 截断），`MedicalAgentService` 与 `EvaluationRunner` 都只依赖它。这样评测才真正守住线上基线，也是 C1 的顺带收益。

### C3 · 响应契约重复：`Result<T>` 有实现，但没有消费者

`AgentController` 里 `Map.of("code",200,"msg","ok","data",…)` 出现 **9 次**（85、98、103、111、118、121、124、131、149）；而 `aimin-common/aimin-base` 里 `Result<T>` 早已存在，admin/auth 全在用。

根因在依赖：`aimin-agent/pom.xml` **不依赖任何 aimin-common 模块**（只有 langchain4j / pdfbox / jdbc / mysql）。于是被迫自造信封，前端 `utils/request.js:105` 又专门写了一段"兼容未包装成 {code,msg,data} 的响应"的兜底——一个后端依赖缺失，前端付了利息。

**建议**：agent 内置 10 行 `record ApiResponse<T>(int code, String msg, T data)`，Controller 统一包装；同时删掉前端那段兼容分支（`request.js:105-107`）——前端只需认一种形状，不必知道代码在哪个模块。

> ⚠️ **不要改成"依赖 `aimin-base`"**（初版建议，已撤回）：base 的 pom 会带入 `nacos-discovery` / `nacos-config` / `spring-cloud-bootstrap` / `spring-boot-starter-data-elasticsearch` / `mybatis-plus-join`。而 agent 刻意 `exclude` 了 `DataSourceAutoConfiguration`，启动命令里也没有 `SPRING_CLOUD_NACOS_*_ENABLED=false`。加 base 会让 agent 启动时尝试注册 Nacos、并激活 ES 自动装配——这不是"一行 pom"，是给做过减法的模块加回当初删掉的东西。详见对抗性审查第五节。

判据：agent 与其他模块**共享的是 JSON 形状，不是代码**。共享形状用 10 行 record 就够，没必要共享 classpath。

### C4 · 抽象缺失，测试被迫继承具体类

`test/.../HybridRetrieverTest.java:21-33`：

```java
static class StubVectorRetriever extends VectorRetriever {
    StubVectorRetriever(List<Evidence> out) { super(null, null); ... }  // 传 null 骗过构造器
}
```

`VectorRetriever` / `Bm25Index` 是具体类、无接口，测试只能继承 + `super(null, null)`。构造器一改（比如加个配置参数），测试立刻编译失败——**这正是"编排层无法单测"的同源病**：依赖的是实现，不是契约。

**建议**：定义 `Retriever` 接口（`List<Evidence> retrieve(String query, int topK)`），`VectorRetriever` / `DrugRetriever` / `HybridRetriever` 实现之；`HybridRetriever` 依赖接口而非实现类。测试改用匿名实现，去掉 `super(null,null)`。

### C5 · admin 的 facade 边界"一半一半"

| Controller | 注入 | 问题 |
|---|---|---|
| `AdminController` | `AdminFacadeService` | ✅ 只走 facade |
| `DepartmentController` | `DepartmentFacadeService` | ✅ |
| `RouterController` | `PermissionFacadeService` | ✅ |
| `PermissionController` | `PermissionFacadeService` **+** `PermissionService` | ❌ 第 94 行直接 `permissionService.getListByPid(pid)` |
| `RoleController` | `RoleFacadeService` **+** `RoleService` | ❌ 第 81 行直接 `roleService.getAll()` |

同一层出现两条调用路径：走 facade 的带事务/审计，绕过 facade 的没有。以后问"这个接口有没有记审计"，得逐个看实现。

**建议**：二选一并贯彻——① facade = 用例边界，controller 只依赖 facade（推荐，改动小，把 2 个直调补进 facade）；② 删掉 facade，服务层直接承担用例（改动大）。现状是最难维护的中间态。

### C6 · 网关策略表与路由表各存一份前缀

`gateway/auth/StrategyFactory.java:22-31` 的 static 块硬编码 `/aimin-auth/**`、`/aimin-admin/**`、`/aimin-agent/**`；网关路由前缀在 `application.yml` 里另有一份。新增服务要改两个文件，且前缀写错不会有任何编译期或启动期报错——只会表现为"路径落到默认拒绝"（安全上还好）或"该保护的没保护"（安全上很糟）。

**建议**：把"前缀 → 策略"下移到 `application.yml`（`aimin.gateway.auth.rules`），`StrategyFactory` 只负责匹配；或让路由与策略共用同一份常量类。当前只有 4 条路由，优先级不高，但属于"迟早会踩"的那类。

### C7 · `aimin-cache` 看似零引用，实为 admin 缓存层的唯一提供者（**初版判断已撤回**）

| 表面证据 | 真实情况 |
|---|---|
| 四个模块 grep `AiminCache\|AiminCacheManager` → 0 命中 | admin 有 `@EnableCaching`（`AiminAdminApplication:11`）+ 9 处 `@Cacheable(keyGenerator = "keyGen")`（`AdminRoleServiceImpl:38…75`、`AdminServiceImpl:83,104,110`）+ `@CacheEvict`（`:81`） |
| 类名没人 import | `keyGen` / `defaultKeyGen` 两个 `KeyGenerator` Bean 与 `AiminCacheManager`，全部由 `AiminCacheAutoConfiguration:69,93` 提供，并经 `META-INF/spring/...AutoConfiguration.imports` 自动装配 |

**结论：不可删。** 删掉 → `keyGen` Bean 缺失导致启动失败；若被 Spring 降级兜底，则 L2 Redis 与缓存同步静默失效，比启动失败更难查。

这次的误判本身就是个教训：**低耦合检查不能只 grep 类名**，还得看注解、SPI、自动装配、配置键四类隐形引用——只盯 import 正是本文第三节批评的那个毛病。

真要减模块，候选是 `aimin-auth`（前端全库 0 次调用、网关仍挂路由、启动需喂 `WX_APPID=dummy`），但那是产品决策，不是纯技术判断（见对抗性审查 B1）。

### C9 · 线程池归属错位

`controller/AgentController.java:37`：`private final ExecutorService executor = Executors.newCachedThreadPool();`

- 无上限（`cachedThreadPool` 最大 Integer.MAX_VALUE），SSE 长连接场景下是资源风险；
- 无 `@PreDestroy`，应用关闭时线程不回收；
- 无命名（线上 dump 里全是 `pool-N-thread-M`）。

线程池是基础设施，应作为 bean 在 `config/` 里提供（带 `corePoolSize/maxPoolSize/queue/rejectedExecutionHandler` 与 Spring 生命周期），Controller 只注入。

## 四、做得好的地方（不要动）

1. **`LlmClient` 抽象 + Mock/DeepSeek 双实现 + `AgentBeans` 集中装配**：依赖倒置到位，无 Key 也能全链路离线跑，这是整个项目最漂亮的一处。
2. **`RiskEvaluator` 纯函数、零依赖、规则集中硬编码**：安全边界就该放在这种"小到无法被绕过、纯到能全量单测"的类里。
3. **网关鉴权用策略模式 + 默认拒绝**：比 if-else 好，扩展点清晰（虽然策略表位置可再优化，见 C6）。
4. **`RrfFusion` / `Bm25Index` / `ChineseTokenizer` 自包含**：无 Spring、无 IO，算法可独立演进——问题只出在"融合被做了两次"（C1），不在于这几个类本身写得差。
5. **admin 用责任链拆创建/删除**（`AdminCreateHandler` / `AdminDeleteHandler`）：把"校验 → 加密 → 建人 → 绑角色"拆成可插拔步骤，比一开始的巨型 service 好。
6. **agent 模块依赖最少**：4 个业务模块里唯一不拖 mybatis/redis/satoken 的，独立部署能力最强——这也是它敢不依赖 common 的底气，只是代价没算清（C3）。
