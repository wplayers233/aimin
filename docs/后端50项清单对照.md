## 五、缓存（21–24）

| # | 项 | 状态 | 取证与判断 |
|---:|---|:--:|---|
| 21 | Cache Invalidation | **险** | 两个问题叠加：① 34 处 `@CacheEvict(value=..., allEntries = true)`，任何一条角色/权限变更都清空整个命名空间，而不是精确失效单 key；② **`@CacheEvict` 在事务提交前执行**——`RoleServiceImpl:29` 是类级 `@Transactional`，方法级 `@CacheEvict` 由 `CacheInterceptor` 在事务提交前触发，存在"清缓存 → 并发线程读到旧值并回填 → 事务才提交"的窗口，脏值会驻留到 180s 后 Caffeine 自然过期。改法（若在意）：`TransactionSynchronization#afterCommit` 里清，或至少在 `clear()` 里去 `KEYS`（见 #23）。 |
| 22 | Redis Eviction | 缺 | `docker-compose-infra.yml` 的 redis 服务**无 `maxmemory`、无 `maxmemory-policy`**，也无 `--maxmemory` 启动参数。默认 `noeviction`：内存打满后所有写命令直接报错，而 `allowNullValues=true` 是专门为"写空值防穿透"配的，一旦写不进去，防穿透机制整体失效并向上抛异常。**改法：加 `--maxmemory 256mb --maxmemory-policy allkeys-lru`，两行。** |
| 23 | Cache Stampedes | 险 | `AiminCache:82-95` 用 8 段 `ReentrantLock` 做单 JVM 内防击穿（`get(key, valueLoader)` 里双重检查），单机有效。**多节点无效**（见 #32）；且 `clear()` 用 `l2RedisCache.keys(cacheName+":*")`（`AiminCache:334`）是全库 `KEYS`，单线程 Redis 上一次 O(N) 阻塞即可造成全体超时。另：`publishMsgPeriodMilliSeconds = 500L`（`AiminCacheConfig:119`）注释声称"防止消息风暴"，**全库只有定义、从未被读取**，节流逻辑不存在。 |
| 24 | Distributed Caching | 险 | Redis 存在但：单点（无 sentinel/cluster）、无降级（`lookup` 直接抛异常，Redis 挂则 38 个 `@Cacheable` 全线失败 + sa-token 全失效 → 网关 401 全站不可用）、`max-wait: -1ms` 无限等待、`timeout: 10s` 对缓存过长。**缓存从加速层变成了单点故障源。** |

## 六、幂等与容错（25–30）

| # | 项 | 状态 | 取证与判断 |
|---:|---|:--:|---|
| 25 | Idempotency | 险 | `MedicalAgentService:306` `consume()` 用 `pendingAsks.remove(sessionId, ask)` 做"值匹配的原子删除"，注释写"避免错误令牌把待确认项销毁"——**并发语义是对的**。但 `pendingAsks` 是 `ConcurrentHashMap`（`:67`），多实例后同一会话可能落到别的节点，`peek` 返回 null → 用户点了"确认"却提示令牌失效。状态外置到 Redis（`SETNX` + TTL）即解决，且顺便拿到 #32 的扩容能力。 |
| 26 | Retry Mechanisms | 缺 | 全库 0 处 retry，LLM 调用失败即失败（`AgentController:55` catch 后 `completeWithError`）。 |
| 27 | Exponential Backoff | 缺 | 同上。 |
| 28 | Jitter | 缺 | 同上。三者应一起做：LLM/HTTP 客户端加重试 + 指数退避 + 抖动，几行装饰器。 |
| 29 | Circuit Breakers | 缺 | 无 Resilience4j / Hystrix / Sentinel。LLM 上游故障时，线程继续无脑排队（见 #47），没有"快速失败"出口。 |

## 十一、该做什么（只留 5 项，全部 ≤ 20 行）

按"改完之后哪件事故不会发生"排序：

| 优先级 | 动作 | 成本 | 消除的风险 |
|:--:|---|:--:|---|
| P0 | `AgentBeans:72` `DriverManagerDataSource` → 有界连接池 | ~5 行 | 并发下 MySQL `Too many connections`（#8） |
| P0 | `AgentController:37` 无界线程池 → 虚拟线程或固定池+有界队列 | ~3 行 | 线程爆炸 / OOM（#37 #47） |
| P1 | redis 加 `maxmemory` + `allkeys-lru`；`max-wait` 改正数、`timeout` 降到 200–500ms | 2 行配置 | Redis 写满后全线报错 + 无限等待雪崩（#22 #24） |
| P1 | `server.shutdown: graceful` + actuator health | 2 行 + 1 依赖 | 重启断流、容器假活（#48 #49） |
| P2 | `AiminCache:334` `KEYS` → `SCAN`；删 `AiminCache:136,146` 两处 `log.info` | ~15 行 | 后台改权限时 Redis 阻塞、日志量=QPS（#23） |

**明确不做**（不是"以后再说"，是这件事不该做）：Flyway 之外的迁移工具、读写分离、分库分表、分区、MQ + DLQ、Outbox、CQRS、Event Sourcing、分布式事务、乐观锁（RBAC 场景冲突极低，加了反而要处理 `OptimisticLockException`）。

**Flyway 单独说明**：它是这 13 项"不做"里唯一可以商量的。当前 4 个脚本靠手工顺序，一旦有第二个人部署或要回滚，成本立刻超过接 Flyway 的成本。但它是"流程卫生"而非"事故预防"，所以没进上面 5 项。
